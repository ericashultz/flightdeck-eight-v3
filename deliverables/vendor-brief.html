Vendor Brief — FLIGHT DECK Activation Hub Page Redesigns

1. Engagement Summary

GE Aerospace runs an internal SharePoint Online site called the FLIGHT DECK Activation Hub in a US Government High (GCCH) tenant. The site documents the company's operating system — fundamentals, behaviors, examples, lean methods. We are redesigning 13 pages total (homepage + 8 fundamentals + 3 behaviors + 1 templates library) and improving the homepage information architecture. The vendor delivers the visual designs as production-ready front-end code.

The vendor will not have access to SharePoint at any point during the engagement. The internal SharePoint developer will deploy and test every deliverable inside the live site by pasting the vendor's code into a PnP Modern Script Editor web part on the corresponding page.

This brief defines exactly what the vendor produces, what is provided to them, and what the acceptance criteria are.

3. Deliverable Format

For each page the vendor delivers one folder containing one file named index.html.

deliverables/
  homepage/
    index.html
  problem-solving/
    index.html
  daily-and-visual-management/
    index.html
  ... (12 folders total)

Hard rules for index.html

1. Single file. All HTML, all CSS, and all JavaScript live in one file. No <link rel="stylesheet">, no <script src="...">, no separate asset files.

2. One root wrapper. All content must be wrapped in <div id="fd-page">…</div>. Nothing renders outside this wrapper.

3. Scoped CSS. Every CSS selector must be prefixed with #fd-page so styles cannot leak into the surrounding SharePoint page chrome.

  • #fd-page .banner { … } ✓
  • .banner { … } ✗
  • body { … } ✗ (forbidden — would override SharePoint)

4. No external network requests at runtime. No CDN scripts, no external fonts, no iframe domains other than those explicitly approved (see Asset Handling). Vendor's index.html must run with the browser offline once the file is loaded. Verified via the browser DevTools Network tab.

5. No external libraries. Vanilla HTML, CSS, and JavaScript only. No React, Vue, Tailwind, GSAP, jQuery, Alpine, etc. Hand-written CSS, hand-written JS. (This is a GCCH constraint — many CDNs are blocked.)

6. Responsive. Must render correctly between 320px and 1600px wide. Required test breakpoints: 1440, 1024, 768, 375.

7. Browser target. Latest Edge and latest Chrome on Windows.

Color, typography & icons — brand kit is authoritative

The official GE Aerospace brand kit in brand-kit/ is the authoritative source for color, typography, and iconography:

  • brand-kit/Visual Identity Toolkit Color - GE Aerospace.pdf
  • brand-kit/Visual Identity Toolkit Typography_Dec2022 - GE Aerospace.pdf
  • brand-kit/Iconography_Library_2Nov23.pptx

shared/design-tokens.css is provided as secondary reference only — it captures what the live SharePoint site *currently* renders (--sp-* variables). Where the brand kit and the live tokens differ, the brand kit wins. Use the tokens to understand the existing look and to keep section bands consistent; use the brand kit to decide the target design.

Typography: the deliverable must not load external web fonts (GCCH blocks external font hosts). Use the system stack so SharePoint's default Segoe UI is honored:

font-family: 'Segoe UI', -apple-system, BlinkMacSystemFont, 'Roboto', sans-serif;

Icons: extract or recreate from the iconography PPTX, but inline every icon as SVG or a data: URI in the final file — no icon fonts, no CDN sprites. See brand-kit/README.md.

4. Asset Handling

Each page folder (pages/<slug>/) ships with real previews so you can design with the actual content in front of you:

  • Real images — pages/<slug>/assets/img/ holds the actual page images. Design with these directly.
  • Document & video posters — pages/<slug>/assets/posters/ holds a rendered thumbnail (JPG) for every PDF, Office file, and video. These are poster frames only — the source files are never provided. Use them as the visual stand-in for document cards and video tiles.
  • asset-manifest.json — every entry carries assetType, the SharePoint url, a localPreview path (when a preview exists), and previewKind (image | poster | placeholder | none). Entries marked placeholder had no renderable preview — use a CSS placeholder for those.

At runtime the deliverable still uses no external requests. Inline the provided previews as local files during design, but the final index.html must reference them as data: URIs or carry a data-asset attribute matching the manifest filename so the internal team swaps in the SharePoint-resolved URL after deployment. No external <img src="https://...">.

<figure class="image-card" data-asset="Problem-Solving-Process.png">

  <figcaption>Problem Solving Process</figcaption>
</figure>

Videos: design poster frames (CSS-drawn or solid-color blocks with overlaid play icon). Do not embed <iframe> or <video> elements pointing at external hosts. Same data-asset convention.

Documents (PDF, PPTX, XLSX): design as cards with file-type icon + label only. The internal team will wire up the click-through URL.

External embeds (Vimeo, YouTube, Microsoft Stream): flag any place an external embed is required. Do not include the iframe in the deliverable — describe what should go there in an HTML comment. The internal team will validate embed reachability in GCCH and wire it in.

5. Visual Fidelity

The vendor designs the body to look natural sitting underneath the native SharePoint suite bar, banner, and navigation. The provided preview.html harness shows what those native elements look like and gives a faithful canvas size and frame.

  • Body container max width: approximately 1204px (modern SP page canvas). Body content is centered.
  • Section background bands: the existing pages use full-bleed colored bands behind certain sections (--zone-emphasis-1 for neutral light gray, --zone-emphasis-2 for soft theme tint). Vendor may use these or propose alternatives.
  • Spacing: modern SP uses 24px vertical padding inside sections and 16px gutters between columns as defaults. Vendor may deviate where the design calls for it.

7. Local Preview Workflow

1. Open preview.html by double-clicking it in your file explorer. It opens in your default browser with no server required.

2. The harness shows a stub of the SharePoint suite bar, banner, and top navigation, plus a page picker and an empty 1204px-wide canvas below.

3. Pick the page you're working on from the dropdown — this sets the category tag and highlights the matching nav item so the frame matches that page's context. (The picker does not load files; preview one page's snippet at a time.)

4. Inside the canvas markup you'll see two HTML comments: VENDOR_SNIPPET_START and VENDOR_SNIPPET_END. Paste your <div id="fd-page">…</div> between them.

5. Reload the file. Use the viewport-control buttons (1440 / 1024 / 768 / 375 / Reset) to verify responsive behavior at each breakpoint.

6. Open DevTools → Network tab. After reload, the only request shown should be the file itself. Any other request fails the deliverable.

8. Acceptance Criteria

A page is accepted when:

  • [ ] One file: index.html containing all HTML, CSS, and JS
  • [ ] All content wrapped in <div id="fd-page">…</div>
  • [ ] Every CSS selector prefixed with #fd-page
  • [ ] No external network requests at runtime (DevTools Network tab shows only index.html)
  • [ ] No external libraries used
  • [ ] Renders correctly at 1440, 1024, 768, and 375px widths
  • [ ] Color & type follow the authoritative brand-kit/ guides; where --sp-* tokens are used they are referenced as variables, not hardcoded hex (allowable exceptions: gradient stops, drop shadows, transparent overlays — call these out in a code comment)
  • [ ] Body text passes WCAG 2.1 AA color contrast (4.5:1 for normal text, 3:1 for large text)
  • [ ] Each placeholder asset carries the data-asset attribute with the matching filename from the manifest
  • [ ] The page renders correctly inside preview.html with no console errors and no unstyled-content flash

9. GCCH-Specific Notes

  • External CDNs are unreliable in GCCH. Many are blocked or rate-limited. The "no external libraries" rule is non-negotiable for this reason, not a stylistic preference.
  • Microsoft Stream is the preferred hosted-video provider on the live site. Vimeo URLs appear in some current pages and may or may not resolve in GCCH — the internal team will validate after deployment.
  • The native SharePoint suite bar adjusts its height based on the user's notification state. Designs should not assume a fixed offset from the top of the viewport.

10. Iteration Loop

1. Vendor delivers a page folder.

2. Internal SP developer pastes index.html contents into the Script Editor web part on the live SP page.

3. Internal team takes screenshots in the live environment and sends annotated feedback.

4. Vendor revises and re-delivers.

5. Repeat until accepted.

There is no shared environment between vendor and SharePoint. All testing on the SharePoint side is the internal team's responsibility.

11. Open Questions for the Vendor to Confirm Before Starting

1. Internationalization — single language (English) only? Confirmed unless raised.

2. Animations — are page-load or scroll-triggered animations expected? If so, performance budget?

3. Print stylesheet — required on any of the 13 pages?

4. Dark mode — required? SharePoint Modern does not currently expose user dark-mode preference inside web parts, so dark mode would need to be a separate toggle.

5. Interactive state — accordions, tabs, modals, filters? List which pages need which.

6. Mobile navigation inside the body — the existing pages have a sticky in-page navigation table on the left. Should the vendor build a mobile-friendly variant (collapsible, sticky bottom bar, dropdown), and which approach is preferred?

Vendor should confirm answers in writing before beginning page 1.

12. Homepage Information Architecture

The homepage redesign includes improving the information architecture — the vendor proposes the new structure. We are not handing you a target IA; we want your recommendation.

Inputs provided for this work:

  • shared/_page-index.json — the full current sitemap (every page in the live site, with title and filename), so you can see the complete content inventory.
  • pages/TopicHome/design-structure.md — the current homepage, section by section.
  • The 13 in-scope pages grouped by category (homepage / 8 fundamentals / 3 behaviors / templates) in §2, which reflects the intended top-level grouping.

What we're looking for: a recommended navigation model and homepage layout that makes the fundamentals, behaviors, examples, and templates easy to find — delivered as part of the homepage design, with a short rationale. The existing top nav is represented in the harness only as a stub; you are not redesigning the SharePoint chrome itself, but your homepage design and IA recommendation should assume a cleaner entry point into these content groups.
